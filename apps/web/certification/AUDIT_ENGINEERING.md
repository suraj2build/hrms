# Engineering Audit — Employee Operating System v1 (Experience Core)

Scope: `apps/api/src/routes/ess/*` + `apps/web/src/components/experience/*` + the
7 ESS experience pages + bundle output. Read-only; every finding grounded in code.

Build measured once: `npx vite build` → exit 0, 25.72s. Key chunks:
- `index-CmuNCYtG.js` — **1,148.88 kB / gzip 299.32 kB** (the eager main chunk)
- `vendor-charts` 444.47 kB / gzip 116.33 kB
- `vendor-xlsx` 424.30 kB / gzip 141.81 kB
- `vendor-supabase` 205.47 kB, `vendor-react` 188.61 kB, `vendor-icons` 109.39 kB

## CRITICAL

### C1 — `/ess/home` is a GET that performs a full-table scan + writes on every request
**File:** `apps/api/src/routes/ess/home.ts:80` → `lib/community-celebrations.ts:40-109`
**Impact:** Every Home load (desktop `EssHome`, `MobileHome`, and `MobileEssShell`
greeting — all share key `['ess-home']`, staleTime 2 min) `await`s
`ensureTodaysCelebrations`, which (a) scans up to **2000 active employees**
(`.limit(2000)`, celebrations.ts:47-51), (b) runs an `existing` feed_posts query,
then (c) **INSERTs feed_posts one-by-one in a sequential loop** (celebrations.ts:96-103).
That is a hidden write on a read endpoint, on the response's critical path, before
the parallel fan-out even starts. Round-trips before the main fan-out: 1 (profile)
+ 1 (employees scan) + 1 (existing posts) + up to N inserts. On a tenant with
birthdays, this serially blocks the Home response by N network inserts.
**Recommendation:** Move celebration generation off the request path — nightly cron
(`runTenantCelebrations`) or fire-and-forget (don't `await`; `void` it after the
response, or a `setImmediate`). At minimum batch the inserts into one
`.insert(rows)` call. Stop scanning 2000 rows synchronously inside a GET.
**Effort:** M

### C2 — `company.ts` scans up to 2000 employees every request to compute today's birthdays in JS
**File:** `apps/api/src/routes/ess/company.ts:55-58, 83-91`
**Impact:** `MyCompany` (key `['ess-company']`, 2-min stale) loads
`employees … .limit(2000)` on **every** request, then filters MM-DD in JS
(`e.dob.slice(5) === todayMMDD`). For a tenant approaching 2000 staff this is a
~2000-row payload (id, names, dob, joining_date) transferred and looped per
request, to surface a handful of celebrants. This is a per-request full-table scan
with no index usable (MM-DD match can't hit a btree on a full date).
**Recommendation:** Either (a) a generated `birth_mmdd`/`join_mmdd` column +
partial index and `.eq('birth_mmdd', todayMMDD)`, or (b) reuse the
`feed_posts` birthday/anniversary system posts (already generated by C1's job) as
the source instead of re-deriving from the roster. Cap the select to needed columns.
**Effort:** M

## HIGH

### H1 — The 7 ESS experience pages are eagerly imported, inflating the 1.1MB main chunk
**File:** `apps/web/src/App.tsx:27-33`
```
import { EssHome }     from '@/pages/ess/EssHome'
import { EssTimeline } from '@/pages/ess/EssTimeline'
import { MyGrowth }    from '@/pages/ess/MyGrowth'
import { MyAttention } from '@/pages/ess/MyAttention'
import { MyTeam }      from '@/pages/ess/MyTeam'
import { MyCompany }   from '@/pages/ess/MyCompany'
import { MyAssistant } from '@/pages/ess/MyAssistant'
```
**Impact:** Every other route in App.tsx uses `lazy()` (224 lazy() calls counted);
these 7 are static, so they + their transitive deps (experience components,
`useTimeline`/`useIdentity`/`useAssistant`, ActivityItem, JourneyRail, etc.) are
bundled into `index-CmuNCYtG.js` = **1,148.88 kB / 299 kB gzip**. They load for
*every* user on first paint — including admins who may never open `/ess`. This is
the single largest avoidable cost in the bundle; index is 2.5× the next chunk.
**Recommendation:** Convert all 7 to `lazy(() => import(...))` like the rest. They
already render under `<Suspense>` route boundaries used elsewhere. Expect the index
chunk to drop materially (these become 7 small route chunks, fetched on navigation).
**Effort:** M

### H2 — Timeline renders all chapters/events with `.map`, no virtualization, with infinite-scroll appending
**File:** `apps/web/src/pages/ess/EssTimeline.tsx:30,66`; hook `useTimeline.ts:60-84`
**Impact:** `useInfiniteQuery` pages by cursor and `useTimeline` *merges all pages'
chapters* into one growing array; `EssTimeline` renders `rest.map(ChapterBlock)`
and each chapter does `c.events.map(ActivityItem)`. There is no windowing. A
long-tenured employee paging deep (each page up to 60 events, CAP 200/source on
the server) accumulates an unbounded DOM. Every `fetchNextPage` re-runs the full
merge+sort+`rangeLabel`/`summaryOf` derivation over *all* loaded items (not memoized).
**Recommendation:** Virtualize the chapter/event lists (`@tanstack/react-virtual`)
or cap rendered chapters; memoize the page-merge with `useMemo` keyed on
`q.data?.pages.length`. The same hook drives mobile, so the fix lands once.
**Effort:** M

### H3 — `projectEvents` re-fetches the entire per-source history (CAP 200 × 5 sources) on every Timeline page
**File:** `apps/api/src/routes/ess/events.ts:91-121`; consumed by `timeline.ts:117`
**Impact:** Timeline keyset pagination is done **in memory**: every page request
calls `projectEvents`, which loads up to 200 leaves + 200 slips + 200 kudos-in +
200 kudos-out + 50 announcements, merges, sorts, then `.filter(at < cursor)` and
slices (events.ts:234-238). So page 2, 3, 4… each re-query and re-project the
*whole* history just to drop the head. Round-trips per Timeline page: 6 (5 sources
+ recognition name resolve) inside projectEvents, plus timeline.ts adds emp +
projectJourney (≥3 more) + first-page recognition counts (2). The cursor saves DB
*rows returned to client* but not DB *work*.
**Recommendation:** Push the cursor into each source query
(`.lt('created_at', cursor)` / `.lt('updated_at', cursor)`) and `.limit(limit)` per
source so deep pages don't re-scan history; or accept it but document the per-source
CAP as the real history ceiling. Indexes on `(tenant_id, employee_id, created_at)`
for recognition and `(employee_id, updated_at)` for payroll_slips.
**Effort:** L

### H4 — `activity.ts` scans up to 500 employees on every Home open just to find today's peer birthdays
**File:** `apps/api/src/routes/ess/activity.ts:92-95`
**Impact:** `['ess-activity']` (60s stale, fired by EssHome) selects
`employees … .not('dob','is',null).limit(500)` and JS-filters `dob.slice(5) === todayMMDD`.
500-row scan per request for, typically, zero-to-few birthdays. Same anti-pattern
as C2 at smaller cap. Combined with home.ts's own 500-row colleague scan (#11) and
C1's 2000-row scan, a single Home paint triggers **three** roster scans
(2000 + 500 + 500) across two endpoints.
**Recommendation:** Source peer birthdays from the celebration `feed_posts`
(type=birthday) instead of re-scanning, or add the generated MM-DD column + index
(shared fix with C2).
**Effort:** M

## MEDIUM

### M1 — Name resolution is a follow-up query (mild N+1) on most surfaces
**Files:** `company.ts:104-106`, `home.ts:260-263`, `team.ts:120-123`,
`signals.ts:138-140`, `activity.ts:134-136`, `events.ts:129-132`, `identity.ts:114-117`,
`journey.ts:78-80`.
**Impact:** Every surface fetches rows holding employee-id FKs (recognition
giver/receiver, approvers), then issues a *second* `employees … .in('id', ids)`
round-trip to resolve names. It's batched (one `.in()` not per-row), so it's a
+1 round-trip, not a true per-row N+1 — except `journey.ts:78-80` which resolves
the first-kudos giver as its own single-row query, and the first-page Timeline
which adds 2 recognition `count` queries (`timeline.ts:213-218`). Per request the
extra hop adds latency serially (it can't start until the parent query returns).
**Recommendation:** Use Supabase FK embeds (`recognition.select('…, from:employees!from_employee(first_name,last_name)')`)
as `home.ts` already does for the feed author embed (`home.ts:155`) and job_history.
Collapses the second hop into the first.
**Effort:** M (per route, S each)

### M2 — `team.ts` "needs a break" insight pulls up to 200 leave rows for reports every request
**File:** `apps/api/src/routes/ess/team.ts:143-146`
**Impact:** Manager view runs an extra `leave_requests … .limit(200)` over all
reports' approved leave, ordered, then JS-reduces to last-leave-per-employee — a
second fan-out after the roster + presence queries. For a manager this makes
`/ess/team` ~7 round-trips (profile, me, roster ×3 parallel, presence+recog ×2
parallel, giver-names, last-leave). Recomputed every 2 min (staleTime) with no caching.
**Recommendation:** `DISTINCT ON (employee_id) … ORDER BY employee_id, to_date DESC`
in one query, or a small daily-cached "stale break" set. Low urgency since it's
gated to managers.
**Effort:** S

### M3 — Assistant is fully non-streaming — whole reply blocks the round-trip
**File:** `apps/web/src/components/experience/useAssistant.ts:76` (`api.post('/assistant/chat')`)
**Impact:** `ask()` awaits the entire LLM reply before any UI update; `asking`
spins until the full completion returns. For multi-sentence answers (and tool use,
`tools_used`) this is several seconds of dead time with no token-by-token feedback —
the worst-feeling latency in the whole experience surface. No optimistic/partial render.
**Recommendation:** Switch `/assistant/chat` to SSE/streaming and render tokens as
they arrive (the page already holds a message thread to append to). If backend
streaming is out of scope, at minimum show a typing indicator + skeleton so
perceived latency drops.
**Effort:** L (needs backend streaming) / S (perceived-latency UI only)

### M4 — `staleTime` inconsistency across the `ess-*` query keys
**Files:** EssHome.tsx:117-129, MyAttention.tsx:42, MyTeam.tsx:57, MyCompany.tsx:51,
useIdentity.ts:30, useTimeline.ts:66, MobileHome.tsx:87-93, MobileEssShell.tsx:61-68.
**Impact:** Same logical key carries different freshness in different files but they
*share* the cache — first mount wins, later mounts' staleTime is ignored. Observed:
`ess-home` 2min everywhere (consistent). `ess-signals` is 60s in EssHome/MyAttention/
MobileHome/MobileEssShell (consistent). `ess-progress`/`ess-reflection` 5min
(consistent). `ess-timeline` 2min, `ess-identity` 5min. This is actually fairly
disciplined; the real risk is **silent divergence** if any future edit sets a
different staleTime on a shared key. No `ess-*` key is missing `staleTime`.
**Recommendation:** Centralize the keys + staleTime in one `essQueries.ts` factory
so the shared-key contract (esp. `ess-signals` used by Home peek + My Attention +
mobile bell) can't drift. Low severity today, prevents a class of bug.
**Effort:** S

### M5 — EssHome has no error surface; a failed `/ess/home` shows an empty skeleton-less page
**File:** `apps/web/src/pages/ess/EssHome.tsx:116-134`
**Impact:** Unlike the other 6 pages (all wire `isError` → `<ErrorState>`), EssHome
only reads `isLoading` and defaults every section to `?? []`/`null`
(`signals = signalsQ.data?.signals ?? []`, etc.). If `/ess/home` itself 500s, the
page renders with `data` undefined and no ErrorState — a blank/degraded Home with
no retry affordance. The sub-queries degrade gracefully, but the primary one has no
error branch.
**Recommendation:** Add `data && isError` → `<ErrorState onRetry={refetch}>` to
EssHome matching the sibling pages.
**Effort:** S

## LOW

### L1 — `MyCompany` feed (`happening`) renders all groups/events un-virtualized
**File:** `apps/web/src/pages/ess/MyCompany.tsx:116,137,153-155`
**Impact:** `c.happening` is capped server-side at 30 feed rows (`company.ts:77`),
so the list is bounded and virtualization isn't needed today. Flag only if the cap
rises. No memoization on the maps, but the dataset is small.
**Recommendation:** Leave as-is; revisit only if the 30-row cap grows.
**Effort:** S

### L2 — Repeated `safe()` / `fullName()` / `BADGE_LABELS` copy-pasted across 6 ess routes
**Files:** company.ts:25-35, team.ts:21-31, signals.ts:52-58, activity.ts:35-41,
events.ts:58-68, identity.ts:22-32, journey.ts:29-31.
**Impact:** Pure maintenance — six near-identical `safe`/`fullName`/`BADGE_LABELS`
definitions. No runtime cost; risk is divergent behavior on edit (e.g. someone fixes
a name fallback in one place only).
**Recommendation:** Hoist to `apps/api/src/routes/ess/_shared.ts`. Cosmetic.
**Effort:** S

### L3 — Per-request `Date`/window recomputation; no cross-request memo of "today's celebrants"
**Files:** company.ts, home.ts, activity.ts (todayMMDD derived + roster scanned per req).
**Impact:** The set of "people celebrating today" is identical for all users in a
tenant for 24h, yet it's recomputed from a roster scan on every user's Home/Company
load. A 5-minute per-tenant in-process cache (or the feed_posts source) would
eliminate the bulk of C2/H4's scans.
**Recommendation:** Memoize today's celebrants per tenant (TTL to next midnight).
Folds into the C2/H4/C1 fixes.
**Effort:** M

## Tenant scoping (correctness/security-adjacent) — PASS

Every ess route filters by `tenant_id` on every sub-query:
- home.ts: all 12 fan-out queries `.eq('tenant_id', tenantId)` (and the manager
  approvals fan-out :230-233, giver resolve :262).
- signals.ts, activity.ts, progress.ts, reflection.ts, team.ts, company.ts,
  identity.ts, events.ts (`projectEvents`), journey.ts, timeline.ts — all
  `.eq('tenant_id', tenantId)` on each `.from()`.
- `getDirectReportIds`/`isDirectReport` (manager-scope.ts) both tenant-filter.
- `ensureTodaysCelebrations` tenant-filters its scan, existing check, and inserts.
No unscoped employee/recognition/leave query found in the ess surface. PASS.

## Error handling (`safe()` coverage) — mostly PASS, two gaps

- `safe()` wraps every sub-query in company.ts, team.ts, signals.ts, activity.ts,
  progress.ts, reflection.ts, events.ts, identity.ts, journey.ts, timeline.ts.
- **Gaps (unguarded supabase calls):** the **profile resolution** at the top of
  every route (`home.ts:63`, `signals.ts:66`, `activity.ts:49`, `progress.ts:63`,
  `reflection.ts:46`, `team.ts:41`, `company.ts` self via profiles, `identity.ts:58`,
  `events.ts:249`, `timeline.ts:105`) is a bare `await … .maybeSingle()` not wrapped
  in `safe()`. It uses destructured `{ data }` so a *query error* returns
  `data=null` (handled), but a *thrown* client/network error would 500 the whole
  surface. Same for `home.ts:260` giver resolve and the manager second-fan-out
  (`home.ts:229-235`) which are bare awaits. Low-likelihood but inconsistent with
  the stated "every sub-query safe()-wrapped" contract.
- Client: 6 of 7 pages have `ErrorState` + `LoadingState`; **EssHome lacks an
  ErrorState branch** (see M5).

**Recommendation:** Wrap the leading profile lookups (or rely on the route-level
error handler returning a degraded shell). S each.
