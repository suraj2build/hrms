Key Relationships Summary

tenant → everything

tenants━━▶profiles, employees, departments, designations, grades, shifts, sites, work_locations, cost_centers …
All rows carry tenant_id for strict data isolation (RLS enforced on every table)

employee → org

employees.department_id→departments
employees.designation_id→designations
employees.grade_id→grades
employees.manager_id→employees (self-ref)

compensation chain

salary_structures→salary_structure_components
salary_structure_components→salary_components
employee_compensations→salary_structures
employee_compensation_components→employee_compensations

payroll chain

payroll_runs━━▶payroll_slips (1:many)
payroll_slips→employees + payroll_runs
epf/esi/ptax_contributions→payroll_runs
advance/loan recovery→payroll_runs

attendance pipeline

attendance_raw_logs (immutable)
▼ processor
attendance_logs (check-in/out pairs)
▼ aggregator
attendance_daily (1 row / emp / date)
▼ payroll
payroll_slips.lop_days

leave → balance

leave_requests (APPROVED)→ atomic fn →employee_leave_balance
leave_accrual_ledger→running balance journal
attendance_daily.status = 'leave'→excludes from LOP

approval workflow

approval_workflow_config (levels)
▼
approval_instances (active chains)
▼
approval_actions (audit log)
Drives leave_requests, attendance_regularisation. DB-level locking prevents concurrent double-approvals.

job history pattern

Both job_history and employee_compensations use the same "close-previous-current" trigger pattern — only one row per employee can have is_current=true (partial unique index). All changes are append-only; history is never deleted.
